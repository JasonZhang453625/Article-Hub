## 1. 产品定义

### 1.1 一句话定位

Article-Hub 是一个本地优先的 **AI-native personal knowledge inbox**：

> **分享即知识化，对话即检索，原文始终可追溯。**

用户从微信、知乎、Bilibili、小红书、X、YouTube 等平台把链接分享到 Article-Hub。应用先可靠接收内容，再自动提取信息、生成统一的 AI 摘要知识卡片、添加标签并建立本地索引。用户回到应用时，不需要翻找收藏夹，而是直接在首页向自己的全部知识库提问。

### 1.2 核心闭环

```text
跨平台分享链接
  → 待处理箱
  → AI 摘要知识卡片
  → 自动标签 + 文件夹建议
  → 本地向量索引
  → 首页全库对话
  → 引用知识卡片
  → 原文追溯
```

该闭环解决的不是“如何保存更多链接”，而是：

> **如何把散落在多个平台、保存后很少回看的内容，转化为能够再次被发现和使用的个人知识。**

### 1.3 产品原则

1. **收集动作不能失败**：分享后立即保存，AI、网络或正文提取失败只能进入待处理箱，不能导致内容丢失。
2. **每条内容先成为统一知识单元**：V2.0 首版中，一篇内容对应一个 AI 摘要知识卡片，也对应一个检索 chunk。
3. **对话必须可追溯**：回答必须基于知识库摘要，并附带可点击引用；摘要中没有答案时必须明确说明。
4. **本地优先、用户控制 AI**：数据、向量索引和处理状态保存在设备本地；AI 请求直连用户配置的模型服务，不经过 Article-Hub 自有后端。
5. **自动化不剥夺控制权**：AI 标签和文件夹分类自动写入并允许编辑；文件夹分类匹配现有文件夹或在必要时新建，但用户始终可以手动移动或重命名。
6. **原文始终保留**：知识卡片替代原页面作为默认阅读入口，但不能替代事实来源；用户始终能打开原页面。

### 1.4 首发用户

首发面向 **所有重度收藏用户**：

- 每周从多个平台保存大量文章、视频或帖子；
- 经常出现“存过，但想不起来在哪里”的情况；
- 希望减少手工整理，同时仍能控制自己的数据；
- 愿意配置自己的 AI 服务，或先把内容放入待处理箱后再统一处理。

专业技术、研究和知识工作者是优先验证 AI 价值与商业化的种子人群，但产品入口与基础流程不限定职业。

## 2. 差异化与边界

### 2.1 差异化

RAG、摘要和语义检索本身不是独有能力。Article-Hub 的差异化来自这些能力组成的完整工作流：

| 维度 | Article-Hub 的重点 |
|---|---|
| 收集入口 | 作为移动系统分享目标，被动接收来自中文互联网与通用网页的链接 |
| 内容处理 | 把不同平台的原页面转成统一、简洁、可检索的知识卡片 |
| 检索范围 | 默认对整个个人知识库提问，不要求先创建 notebook 或选择资料集 |
| 数据控制 | 本地存储、本地索引、BYOK、无 Article-Hub 自有 AI 后端 |
| 证据链 | AI 回答引用知识卡片，知识卡片继续回链原页面 |

NotebookLM 等产品擅长对用户主动组织的一组来源进行深度研究；Readwise 等产品擅长阅读、标注与全文检索。Article-Hub 优先解决的是：**跨平台内容进入个人知识库之前的低摩擦收集、统一知识化和全库召回。**

### 2.2 非目标

- V2.0 首版明确不做：

- NotebookLM 式的项目型多源研究工作台；
- 基于全文切块的深度事实问答；
- 通用互联网搜索或自动发现外部资料；
- 播客、PPT、报告等多模态内容生成；
- Article-Hub 托管的 AI API、集中式内容后端或默认行为追踪；
- 账号体系与云同步主线；
- 长期聊天记录与跨会话记忆。

上述能力只有在“分享 → 知识化 → 全库召回”核心闭环通过行为数据验证后，才重新评估。

- 向量相似度召回（cosine similarity, top-k, 最低门槛）与关键词降级；
- 四入口底部导航（Chat / Knowledge / Progress / Settings），StatefulShellRoute；
- RAG 对话首页：查询 → 召回 → 候选摘要 → AI 回答 + 引用知识卡片，信息不足时拒绝编造。

- 底部导航缺少隐藏"进程"选项卡的选项；
- 知识库搜索框缺少点击外部自动失焦行为；
- 缺少字体粗细设置。

## 4. 信息架构

移动端主导航默认为四个入口（支持设置中隐藏"进程"入口）：

| 入口 | 核心任务 |
|---|---|
| **对话** | 向全部已知识化内容提问，查看带引用的回答 |
| **知识库** | 浏览、搜索、筛选、编辑知识卡片，管理标签和文件夹 |
| **进程** | 查看处理中、失败和等待配置 AI 的内容，执行重试或删除 |
| **设置** | 配置 AI/embedding、隐私、备份、显示和索引管理 |

手动添加入口放在知识库页或全局快捷入口。文件夹、标签和传统关键词搜索属于知识库能力，不与对话首页争夺主入口。

## 5. 核心用户流程

### 5.1 分享并知识化

1. 用户在其他 App 中点击“分享至 Article-Hub”。
2. Article-Hub 立即保存 URL、来源、接收时间和可用元数据，并显示保存成功。
3. 新条目进入待处理箱，按顺序执行正文提取、摘要生成、自动标签、文件夹建议和 embedding。
4. 全部必要步骤成功后，条目从待处理箱进入知识库。
5. 任一步骤失败时保留条目、失败阶段和错误原因，允许后台或手动重试。

### 5.2 向知识库提问

1. 用户在对话首页输入主题词或具体问题，例如“汽车”或“我收藏过哪些关于新能源汽车竞争格局的观点？”
2. 系统从本地索引召回相关摘要；embedding 不可用时降级为关键词召回。
3. 系统把候选摘要发送到用户配置的聊天模型，要求只基于候选内容回答。
4. 页面展示回答和引用知识卡片。
5. 用户可以打开知识卡片、查看原页面，或反馈答案是否有用。

### 5.3 信息不足

如果召回为空，或候选摘要不包含回答所需事实：

- 不生成看似确定的答案；
- 明确提示“当前知识库摘要中没有足够信息”；
- 在存在弱相关内容时展示相关卡片；
- 提供打开原文或调整问题的入口。

## 7. 产品与数据契约

### 7.1 Article 兼容性

- 保留现有 `Article` 类名和 Hive typeId `0`。
- 保留历史 Hive box 名称 `'passages'`。
- 现有 `Article.summary` 继续作为首版唯一规范化知识 chunk。
- 新字段必须继续使用手写 `TypeAdapter`，并以空值兼容旧数据。

已新增的处理状态字段（V2.0.0，Phase 1.1）：

- `processingStatus`：`ProcessingStatus` 枚举（pending / processing / completed / failed），默认 completed；
- `processingStage`：`ProcessingStage` 枚举（metadata / content / summary / tags / folderSuggestion / indexing），可空；
- `processingError`：`String?`，失败原因；
- `retryCount`：`int`，默认 0；
- `lastProcessedAt`：`DateTime?`，最后处理时间；
- `suggestedFolderId`：`String?`，AI 建议的文件夹 ID。

Hive field 编号 13-18，旧数据自动降级为 completed / null / 0。

### 7.2 索引契约

- 向量输入：`title + summary + tags`。
- 索引记录至少包含 `articleId`、embedding 模型标识、内容指纹和向量。
- 索引是派生数据，可删除、可重建，不进入 JSON 备份。
- Article 删除或摘要变化后，旧索引不得继续被召回。

### 7.3 AI 回答契约

对话结果至少包含：

- 回答正文；
- 使用的 `articleId` 引用列表；
- 是否因信息不足而降级；
- 本次使用的召回方式：语义或关键词。

模型输出中的未知 articleId 必须被过滤，不得生成失效引用。

## 8. 非功能需求

- **可靠性**：分享接收成功后必须先持久化再处理；后台失败不能丢失条目。
- **性能**：对话提交后先快速展示检索状态；本地召回不因知识库规模增长而阻塞 UI。
- **离线**：离线时可收集、浏览、管理和关键词搜索；AI 与 embedding 显示等待状态。
- **隐私**：无 Article-Hub 自有内容后端；用户内容只发送到用户主动配置的 AI 服务。
- **成本控制**：批量摘要、重新索引和模型切换前提示潜在 API 成本。
- **兼容性**：Hive schema 向后兼容；Android、iOS、Web、Windows、macOS 保持可构建。
- **可访问性**：关键触控目标不小于 48×48，状态和错误不能只依赖颜色表达。
- **平台适配**：状态栏文字颜色根据应用背景亮度自动反转 — 浅色背景时使用深色文字（或浅色指示条），确保始终可见。

## 9. 成功指标

### 9.1 北极星指标

**每周成功知识召回次数**

一次成功知识召回应同时满足：

1. 用户通过对话提交问题；
2. 系统生成带有效引用的回答；
3. 用户通过“有用”反馈或点击引用知识卡片表达结果具有价值。

### 9.2 配套指标

| 指标 | 用途 |
|---|---|
| 分享后持久化成功率 | 验证收集动作是否可靠 |
| 知识化完成率与中位耗时 | 验证处理流水线 |
| 待处理失败率与积压量 | 发现模型、网络和提取问题 |
| 摘要有用率 | 验证知识卡片质量 |
| 对话无结果率 | 判断摘要召回覆盖度 |
| 回答有用率 | 判断 RAG 回答价值 |
| 引用点击率 | 判断回答是否推动用户继续使用知识 |
| 关键词降级占比 | 判断 embedding 兼容性 |

指标默认保存在设备本地。需要汇总研究时，由用户主动参与测试或导出匿名统计，不引入默认行为追踪。

## 10. 调研证据与新押注

2026-06-02 的 107 份问卷验证了：

- 收藏分散与保存后很少回看是普遍痛点；
- 文件夹标签和系统分享保存是高优先需求；
- AI 摘要整体意愿一般，但在技术与研究人群中更高；
- 59% 用户偏好本地与 AI 可切换，支持本地优先与 BYOK。

完整分析见 [`调研分析报告.md`](./调研分析报告.md)。

本 PRD 的 AI-first 方向是一次新的产品押注：它不再把 AI 仅作为可选摘要按钮，而是把“知识化与再次召回”作为产品主价值。现有问卷只验证了意愿与痛点，尚未验证用户是否会持续通过对话找回知识。因此，Phase 1–3 必须用真实行为指标验证，不能把方向判断当成已经成立的事实。
